## On-screen controls — `OnScreenButton` / `OnScreenStick`

`OnScreenButton` and `OnScreenStick` (namespace `UnityEngine.InputSystem.OnScreen`) are touchscreen widgets that inject input as if it came from a real device: each references a **control path** (e.g. `<Gamepad>/buttonSouth`), and when the widget is interacted with, the Input System creates a **virtual device** matching that path and reports the interaction as if that real device control had been actuated. If one on-screen button references a `Gamepad` control and another on the same screen references a `Keyboard` control, the system creates *both* a virtual Gamepad and a virtual Keyboard — worth double-checking that every on-screen control on a given screen targets the same intended virtual device, since a mismatch silently spins up an extra device rather than erroring.

On-screen controls have **no built-in visual representation** — a designer/engineer must add the actual sprite/graphic (this half is `ui-ux-programmer`'s territory; this skill's contribution stops at the `OnScreenButton`/`OnScreenStick` component's control-path wiring and the virtual device it produces). `OnScreenButton` implements `OnPointerDown`/`OnPointerUp` (via uGUI's `IPointerDownHandler`/`IPointerUpHandler`), so it plugs into the same `EventSystem`/Graphic Raycaster pipeline as any other uGUI element.

A **custom on-screen control** subclasses `OnScreenControl` directly when neither built-in widget fits (e.g. a rotary dial, a multi-directional swipe pad) — implement the control-path reporting logic per [introduction-on-screen-controls.html](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.20/manual/introduction-on-screen-controls.html)'s "Create a custom on-screen control" guidance rather than reinventing device injection from scratch.

## XR / Tracked devices — boundary, not a deep-dive

`TrackedDevice` (base class, namespace `UnityEngine.InputSystem`) represents any device with tracked position/orientation. The two components this skill's scope actually reaches:

- **`TrackedPoseDriver`** (`UnityEngine.InputSystem.XR`) — drives a GameObject's `transform.position`/`rotation` from a tracked device's pose, via `positionInput`/`rotationInput` (`InputActionProperty`) and a `trackingType` (position only / rotation only / both). **`positionAction`/`rotationAction` are Obsolete on this class — use `positionInput`/`rotationInput` instead**, per `coding-principles.md`'s Obsolete APIs rule; never author new code against the deprecated pair.
- **`TrackedDeviceRaycaster`** — the XR/AR equivalent of `GraphicRaycaster`, casting a ray from a tracked controller into world-space UI instead of from a 2D screen point.

**This is the extent of this skill's XR coverage.** Raw XR *device input* (a controller's pose/button state arriving through `TrackedPoseDriver`/`TrackedDevice`) is in scope; XR *rendering* (stereo rendering, XR Plugin Management, render pipeline configuration for headsets) and the **XR Interaction Toolkit** package (`com.unity.xr.interaction.toolkit` — grab interactables, teleportation, ray interactors) are a different, much larger surface this skill deliberately does not deep-dive into. Flag any task that turns out to actually need XR Interaction Toolkit or XR rendering configuration back as out of scope rather than improvising an answer from general Input System knowledge — this project currently has no dedicated skill covering that package, so surface the gap explicitly instead of guessing.
