# Spatial Queries, Collision/Trigger Events & Simulation Modification

Covers SKILL.md steps 6, 7, 8 (choosing a query type, reading events at the right time, and reaching for deeper pipeline hooks only when justified).

## Manual
- [Collision queries](https://docs.unity3d.com/Packages/com.unity.physics@6.6/manual/collision-queries.html) — five query types: **ray cast** (all or closest intersections for an oriented line segment), **collider cast** (sweeps a collider along a path, stops at first contact), **collider distance** (closest points between shapes within a radius), **point distance** (nearest surfaces to a point), **overlap** (bodies whose bounding boxes intersect a region). Queries run against a single collider or an entire `CollisionWorld` (accessed via `PhysicsWorldSingleton`); world-wide queries use an internal bounding-volume-tree acceleration structure. Standard pattern: get the `CollisionWorld` singleton, build an input struct (`RaycastInput`, `ColliderCastInput`, etc.), call `CastRay()`/`CastCollider()`/etc. Filtering is the preferred, data-driven way to control which results a query returns. The docs recommend running queries inside Burst-compiled jobs, not main-thread C#, for parallelism and optimization (Burst-eligibility verification itself belongs to `unity-burst-compiler`).
- [Simulation results](https://docs.unity3d.com/Packages/com.unity.physics@6.6/manual/simulation-results.html) — reading collision/trigger events after a step: either direct access via `GetSingleton<SimulationSingleton>().AsSimulation()`'s `CollisionEvents`/`TriggerEvents` streams, or scheduling `ICollisionEventsJob`/`ITriggerEventsJob` (`Schedule()` serially or `ScheduleParallel()`). Trigger colliders never physically collide — they raise a trigger event where a collision would otherwise have occurred. **Events are valid only after `PhysicsSimulationGroup` finishes and until it starts again next frame** — reading outside that window gets stale/empty data.
- [Modifying simulation behavior](https://docs.unity3d.com/Packages/com.unity.physics@6.6/manual/simulation-modification.html) — two ways to override default behavior: (1) direct `PhysicsWorld` modification after `PhysicsInitializeGroup`, via `GetSingletonRW<PhysicsWorldSingleton>()` and `PhysicsWorldExtensions` methods (e.g. applying impulses); (2) pipeline interception at four points inside `PhysicsSimulationGroup` — `IBodyPairsJob` (after broadphase, to disable/filter interactions), `IContactsJob` (after narrowphase, to modify contact normals/distances), `IJacobiansJob` (after constraint setup, to adjust friction/constraints), or a final pre-solve hook. Interception systems need correct `[UpdateAfter]`/`[UpdateBefore]` placement and `GetSingletonRW()` access; `Custom Physics Body Tags` are recommended for fine-grained filtering of which entities a modification affects, rather than reaching for interception when a simpler filter would do.

## Scripting API
- [`Unity.Physics.CollisionWorld`](https://docs.unity3d.com/Packages/com.unity.physics@6.6/api/Unity.Physics.CollisionWorld.html) — the queryable spatial structure queries run against.
- [`Unity.Physics.SimulationSingleton`](https://docs.unity3d.com/Packages/com.unity.physics@6.6/api/Unity.Physics.SimulationSingleton.html) — the singleton exposing `AsSimulation()` for direct event-stream access.

Scheduling any of the job types named here (`ICollisionEventsJob`, `ITriggerEventsJob`, `IBodyPairsJob`, `IContactsJob`, `IJacobiansJob`) — dependency wiring, `.Complete()`, disposal — is `unity-job-system-and-burst`'s territory, not this skill's; this file covers only which physics-specific interface/query to reach for.
