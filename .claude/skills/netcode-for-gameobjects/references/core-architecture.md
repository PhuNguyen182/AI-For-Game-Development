## Network topologies
| Topology | What it decides | Source |
|---|---|---|
| `NetworkTopologyTypes.ClientServer` | A single server instance holds authority; every client sends updates to the server and the server runs the simulation. Two sub-architectures: dedicated server (separate machine) or listen-server/host (server + one local client on the same instance). | [Network topologies](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/terms-concepts/network-topologies.html) |
| `NetworkTopologyTypes.DistributedAuthority` | No server simulates the game; a lightweight central state service (CMB) routes traffic while each connected instance simulates the subset of objects it owns. Only supported by `UnityTransport`. | [NetworkTopologyTypes API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.NetworkTopologyTypes.html), [Network topologies](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/terms-concepts/network-topologies.html) |
| Cost trade-off | Client-Server with a dedicated server is the most expensive option (separate hosting); listen-server is cheap (no dedicated infra) but ties world lifetime to the host player. Distributed Authority has no dedicated-server cost at all. | [Network topologies](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/terms-concepts/network-topologies.html), [Listen server and host architecture](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/learn/listenserverhostarchitecture.html) |
| Security trade-off | Client-Server (especially dedicated server) resists compromised/cheating clients because the server is the sole authority. Distributed Authority assumes trustworthy clients since each client simulates its own objects — pick it only when cheat resistance isn't a hard requirement. | [Network topologies](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/terms-concepts/network-topologies.html) |
| When to choose which | Client-Server: need centralized trusted authority and/or client-side prediction with rollback. Distributed Authority: need lower dev/ops cost and simple synchronized spawning without running full server-side simulation. | [Network topologies](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/terms-concepts/network-topologies.html) |

## Authority model
| Item | What it decides | Source |
|---|---|---|
| `HasAuthority` (on `NetworkObject` and `NetworkBehaviour`) | The single property to check before running authoritative logic; works identically as a concept across both topologies but resolves to "is server" in Client-Server and "is owner" in Distributed Authority. Check it before any authoritative code in `Update()`/`OnNetworkSpawn()`. | [Authority](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/terms-concepts/authority.html) |
| Non-authority state changes | A non-authority instance cannot mutate the world directly — it must communicate with the authority and have the authority act on its behalf (an RPC to the server in Client-Server, or a request to the owner in Distributed Authority). | [Authority](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/terms-concepts/authority.html) |
| State storage in Distributed Authority | Must use `NetworkVariable<T>`, not a plain local field/property — DA automatically configures every `NetworkVariable` with owner-write/everyone-read permissions, which is what preserves state correctly across disconnects and ownership transfers. | [Authority](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/terms-concepts/authority.html) |

## Client-server roles
| Property/role | What it decides | Source |
|---|---|---|
| `IsServer` | True on the single authoritative instance; use it to gate spawn logic, gameplay rule validation, and any write the topology reserves to the server. | [Client-server](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/terms-concepts/client-server.html) |
| `IsHost` | True only on a listen-server instance (server + local client combined on one machine); use it to skip resource-heavy work the local client doesn't need duplicated. | [Client-server](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/terms-concepts/client-server.html) |
| `IsClient` | True for every client-side instance, **including the host** — this is not "not-server." Use it for UI/input/effects that every client-side view needs. | [Client-server](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/terms-concepts/client-server.html) |
| Dedicated server | Runs only the simulation, no local player — highest performance/security, highest infra cost; enables prediction/rollback for competitive genres. | [Client-server](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/terms-concepts/client-server.html), [Listen server and host architecture](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/learn/listenserverhostarchitecture.html) |
| Listen server / host | One machine runs server + client. Host's own connection quality and machine load directly affect every other player's experience; host has access to all world data (cheat risk); the session ends when the host disconnects. Fits small groups (<12 players per the manual's stated ceiling) with non-persistent worlds. | [Listen server and host architecture](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/learn/listenserverhostarchitecture.html) |
| State flow constraint | Every state change routes client → server → other clients — no peer-to-peer shortcut — which adds latency versus a distributed model but keeps a single conflict-resolution point. | [Client-server](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/terms-concepts/client-server.html) |

**Critical caveat**: `IsClient` returns `true` on the host as well as on remote clients. Code that means "run this only on a remote client, not the host" must check `!IsHost` explicitly — `IsClient` alone silently double-runs the logic on host builds.

## Ownership model
| Item | What it decides | Source |
|---|---|---|
| Ownership vs. authority | Ownership grants a client-side "loan" of some authority (client-side reactivity) without making the client the ultimate authority — distinct from `HasAuthority`. | [Ownership](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/terms-concepts/ownership.html) |
| Client-Server ownership | Server retains full authority regardless of who owns an object. Ownership only matters for the specific features explicitly configured owner-authoritative: `NetworkTransform` (owner-authoritative mode), `NetworkObject.AllowOwnerToParent`, `NetworkVariableWritePermission.Owner`. | [Ownership](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/terms-concepts/ownership.html) |
| Distributed Authority ownership | The owner of a `NetworkObject` **is always** the authority for that object — ownership and authority collapse into one concept, unlike Client-Server. | [Ownership](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/terms-concepts/ownership.html) |
| `IsOwner` | Available on both `NetworkObject` and `NetworkBehaviour`; the one check that works the same way in both topologies to test local ownership. | [Ownership](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/terms-concepts/ownership.html) |
| Default owner on `Spawn()` | Server-owned in Client-Server topology; caller-owned in Distributed Authority topology — the two topologies disagree on the default, so an unqualified `Spawn()` call means different things depending on which is active. | [NetworkObject ownership (manual)](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/components/core/networkobject-ownership.html) |
| Who can change ownership | Client-Server: only the server. Distributed Authority: the current authority, gated further by `OwnershipStatus` permission flags (see next section). | [Ownership](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/terms-concepts/ownership.html) |

## NetworkObject ownership control
| Method/property | What it decides | Source |
|---|---|---|
| `ChangeOwnership(ulong newOwnerClientId)` | Client-Server: server-only call. Distributed Authority: callable by the current authority; a non-authority call can fail depending on `OwnershipStatus` permissions. | [NetworkObject ownership (manual)](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/components/core/networkobject-ownership.html), [NetworkObject API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.NetworkObject.html) |
| `RemoveOwnership()` | Client-Server topology only — returns ownership to the server; no Distributed Authority equivalent since ownership always exists there. | [NetworkObject ownership (manual)](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/components/core/networkobject-ownership.html) |
| `RequestOwnership()` | Only meaningful when the object's `OwnershipStatus` includes `RequestRequired`; returns an `OwnershipRequestStatus`, and the current owner approves/denies via the `OnOwnershipRequested` callback. | [NetworkObject ownership (manual)](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/components/core/networkobject-ownership.html) |
| `SpawnWithOwnership(ulong clientId, bool destroyWithScene = false)` | Spawns owned by a different client than the spawner; the spawner becomes only a limited "spawn authority," not the owner — owner-specific checks won't fire on the spawner's side. | [NetworkObject ownership (manual)](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/components/core/networkobject-ownership.html), [NetworkObject API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.NetworkObject.html) |
| `SetOwnershipLock(bool)` / `IsOwnershipLocked` | Temporarily blocks any ownership change while locked — use to prevent a transfer mid-transaction (e.g. mid-request). | [NetworkObject ownership (manual)](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/components/core/networkobject-ownership.html) |
| `OnOwnershipPermissionsFailure` / `OnOwnershipRequestResponse` | Callbacks that fire respectively when a change attempt is rejected by permissions, and when a request's approval/denial result comes back. | [NetworkObject ownership (manual)](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/components/core/networkobject-ownership.html) |

| `OwnershipStatus` flag (Distributed Authority) | What it decides | Source |
|---|---|---|
| `None` | Cannot be distributed, requested, or transferred at all. | [NetworkObject.OwnershipStatus API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.NetworkObject.OwnershipStatus.html) |
| `Distributable` | Automatically redistributed to another client when a client joins or leaves — unless locked or a request is already pending. | [NetworkObject.OwnershipStatus API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.NetworkObject.OwnershipStatus.html) |
| `Transferable` | Any non-owner client can take ownership immediately, without a request, as long as it isn't locked. | [NetworkObject.OwnershipStatus API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.NetworkObject.OwnershipStatus.html) |
| `RequestRequired` | A non-owner must call `RequestOwnership()` and get approval before taking ownership; the object is automatically locked once transferred. | [NetworkObject.OwnershipStatus API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.NetworkObject.OwnershipStatus.html) |
| `SessionOwner` | Ownership is pinned to whichever client is the current session owner, and auto-transfers whenever session ownership itself changes — see [distributed-authority.md](distributed-authority.md) for session-owner mechanics. | [NetworkObject.OwnershipStatus API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.NetworkObject.OwnershipStatus.html) |
| `All` | Inspector-only convenience: first selection sets `Distributable`+`Transferable`+`RequestRequired` together; selecting again switches to `SessionOwner` alone. Not a distinct runtime flag combination to reason about in code. | [NetworkObject.OwnershipStatus API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.NetworkObject.OwnershipStatus.html) |

**Critical caveat**: after `SpawnWithOwnership`, avoid editing the object locally on the spawner right away — the spawner is not the owner, so owner-authoritative checks silently don't run there. Prefer `Spawn()` + adjust + `ChangeOwnership()` when the spawner needs to touch the object first.

## Connection approval
| Item | What it decides | Source |
|---|---|---|
| Enabling it | Set `NetworkConfig.ConnectionApproval = true` **and** assign `NetworkManager.ConnectionApprovalCallback`; with the flag on but no callback assigned, connections still auto-approve — the flag alone doesn't add scrutiny. | [Connection approval](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/connection-approval.html) |
| Callback signature | `void ApprovalCheck(NetworkManager.ConnectionApprovalRequest request, NetworkManager.ConnectionApprovalResponse response)`. | [Connection approval](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/connection-approval.html) |

Fix: put shared setup in one method both `Start()` and `OnNetworkSpawn()` call, guarded so it only runs once.

## NetworkBehaviour synchronization
| Mechanism | What it decides | Source |
|---|---|---|
| `NetworkVariable<T>` (tick-based) | Guarantees eventual state synchronization but **not** ordering — dirty variables are queued during late update, so simultaneous changes across multiple objects can be applied client-side in a different order than they happened server-side. | [NetworkBehaviour synchronization](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/components/core/networkbehaviour-synchronize.html) |
| RPCs | Queue immediately into the outbound send queue in call order, preserving relative ordering — the better choice when strict ordering matters more than periodic-tick delivery. | [NetworkBehaviour synchronization](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/components/core/networkbehaviour-synchronize.html) |
| `OnSynchronize<T>(ref BufferSerializer<T> serializer)` | Override to add custom data to the late-join/synchronize payload; combined with RPCs it's how a late-joining client gets caught up on ordered state. | [NetworkBehaviour synchronization](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/components/core/networkbehaviour-synchronize.html), [NetworkBehaviour API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.NetworkBehaviour.html) |
| `OnSynchronize` invocation split | Invoked **server-side only during the write half** of serialization, and **client-side only during the read half** — it never runs the "other" half on either side. | [NetworkBehaviour synchronization](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/components/core/networkbehaviour-synchronize.html) |
