Covers: SKILL.md §4 — **"Route scene loads through NetworkSceneManager once scene management is enabled"**.

This file holds the concrete API surface, event ordering, and gotchas for NGO's integrated scene management (`NetworkSceneManager`), the alternative custom-management path, and the session/reconnection patterns layered on top. It exists to stop scene loads and reconnect logic from silently bypassing NGO's synchronization pipeline.

## Scene management basics

| Fact | What it decides | Source |
|---|---|---|
| Integrated scene management is enabled by default ("Enable Scene Management" toggle on `NetworkManager` in the Inspector) | Out of the box, all scene loads for the networked session must route through `NetworkSceneManager`, not raw `SceneManager` | [Scene management](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/scene-management.html) |
| Two modes: **Integrated** (default) vs **Custom** (disable the toggle) | Custom management is explicitly documented as "time consuming and complex," recommended only for developers already experienced with NGO | [Scene management](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/scene-management.html) |
| Access pattern: `NetworkManager.SceneManager` (from inside a `NetworkBehaviour`) or `NetworkManager.Singleton.SceneManager` (elsewhere) | How code anywhere in the project reaches the active `NetworkSceneManager` instance | [Using NetworkSceneManager](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/using-networkscenemanager.html) |
| `NetworkSceneManager.LoadScene(string sceneName, LoadSceneMode loadSceneMode)` — server/host only, returns `SceneEventProgressStatus`; scene must be registered in "Scenes in Build" | Only the server/host may initiate a scene load; the scene must exist in build settings, even a blank placeholder for dynamically-generated content | [Using NetworkSceneManager](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/using-networkscenemanager.html), [NetworkSceneManager API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.NetworkSceneManager.html) |
| `NetworkSceneManager.UnloadScene(Scene scene)` — server/host only, returns `SceneEventProgressStatus` | Cannot unload the currently active scene — only scenes that were loaded additively qualify | [Using NetworkSceneManager](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/using-networkscenemanager.html) |
| Only one scene event may be in progress at a time | A second `LoadScene`/`UnloadScene` call while one is running returns `SceneEventInProgress` instead of starting | [Using NetworkSceneManager](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/using-networkscenemanager.html) |
| `NetworkSceneManager.VerifySceneBeforeLoading` — server-side delegate | Lets the server reject a scene load/unload before it starts; a `false` return produces `SceneFailedVerification` | [Using NetworkSceneManager](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/using-networkscenemanager.html) |
| `NetworkSceneManager.DisableValidationWarnings(bool disabled)` | Toggles console warnings NGO logs about scene invalidation issues | [NetworkSceneManager API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.NetworkSceneManager.html) |
| `NetworkSceneManager.GetSynchronizedScenes()` / `GetSceneMapping(MapTypes)` | Query which scenes are currently loaded and tracked by the active session, and the client↔server scene handle mapping | [NetworkSceneManager API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.NetworkSceneManager.html) |

**Critical caveat**: once "Enable Scene Management" is on, calling `UnityEngine.SceneManagement.SceneManager.LoadScene`/`LoadSceneAsync` directly bypasses `NetworkSceneManager` entirely — no `SceneEventType.Load` fires, connected and late-joining clients never receive a synchronization message for that scene, and any in-scene placed `NetworkObjects` in it never spawn on clients. Every scene load once scene management is enabled must go through `NetworkManager.SceneManager.LoadScene(...)`.

## Scene events and client synchronization mode

`NetworkSceneManager.OnSceneEvent` fires for every `SceneEventType`; there are also per-type delegates (`OnLoad`, `OnLoadComplete`, `OnLoadEventCompleted`, `OnUnload`, `OnUnloadComplete`, `OnUnloadEventCompleted`, `OnSynchronize`, `OnSynchronizeComplete`). **Critical caveat**: subscribe to these immediately after `StartServer()`/`StartHost()`/`StartClient()` — subscribing inside `OnNetworkSpawn` is too late to catch the `Synchronize` event for a newly-connecting client.

| `SceneEventType` value | Direction / meaning | Source |
|---|---|---|
| `Load` | Server → client: a scene load has started | [SceneEventType API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.SceneEventType.html) |
| `LoadComplete` | Client → server: this client finished loading the scene | [SceneEventType API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.SceneEventType.html) |
| `LoadEventCompleted` | Server → client: every client has finished loading | [SceneEventType API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.SceneEventType.html) |
| `Unload` | Server → client: a scene unload has started | [SceneEventType API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.SceneEventType.html) |
| `UnloadComplete` | Client → server: this client finished unloading | [SceneEventType API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.SceneEventType.html) |
| `UnloadEventCompleted` | Server → client: every client has finished unloading | [SceneEventType API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.SceneEventType.html) |
| `Synchronize` | Server → client: initial session state (scenes + pre-ordered `NetworkObject` list) sent to a newly-approved client | [SceneEventType API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.SceneEventType.html) |
| `SynchronizeComplete` | Client → server: client finished processing `Synchronize` and spawning its objects | [SceneEventType API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.SceneEventType.html) |
| `ReSynchronize` | Server → client: resends IDs of objects that were despawned mid-synchronization | [SceneEventType API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.SceneEventType.html) |
| `ActiveSceneChanged` | Synchronizes clients when the server's active scene changes | [SceneEventType API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.SceneEventType.html) |
| `ObjectSceneChanged` | Synchronizes clients when one or more `NetworkObjects` migrate into a different scene | [SceneEventType API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.SceneEventType.html) |

`SceneEvent` (the payload passed to these callbacks) carries: `SceneEventType`, `ClientId` (`ulong`, meaning depends on event type), `SceneName`, `ScenePath`, `Scene`, `LoadSceneMode`, `AsyncOperation` (Load/Unload only), `ClientsThatCompleted` (`List<ulong>`), `ClientsThatTimedOut` (`List<ulong>`). Source: [SceneEvent API](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/api/Unity.Netcode.SceneEvent.html).

| Client synchronization mode fact | What it decides | Source |
|---|---|---|
| `NetworkSceneManager.SetClientSynchronizationMode(LoadSceneMode mode)` sets it; `ClientSynchronizationMode` (read-only) reports it | Governs how a connecting client reconciles its own already-loaded scenes against the server's scene list | [Client synchronization mode](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/client-synchronization-mode.html) |
| `LoadSceneMode.Single` | Client unloads all its currently loaded scenes first, single-loads the server's active scene, then additively loads the rest the server has loaded | [Client synchronization mode](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/client-synchronization-mode.html) |
| `LoadSceneMode.Additive` | Client keeps scenes it already has loaded and only additively loads whatever the server has that it's missing — cuts sync time for shared/bootstrap scenes | [Client synchronization mode](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/client-synchronization-mode.html) |
| `NetworkSceneManager.PostSynchronizationSceneUnloading` (additive mode only) | Flag to unload any client-side scene that wasn't part of the server's synchronized set, once sync finishes | [Client synchronization mode](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/client-synchronization-mode.html) |
| `NetworkSceneManager.VerifySceneBeforeUnloading` (additive mode only) | Client-side delegate to selectively keep a scene alive during post-sync cleanup instead of letting it be auto-unloaded | [Client synchronization mode](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/client-synchronization-mode.html) |
| Default mode value | Not stated on this page — treat as undocumented and verify in-Editor rather than assuming | [Client synchronization mode](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/client-synchronization-mode.html) |

### Timing / ordering facts

| Fact | Constraint it enforces | Source |
|---|---|---|
| Sync order: connection approval → server sends `Synchronize` → client processes it and spawns objects → client sends `SynchronizeComplete` | `NetworkManager.IsConnectedClient` only becomes `true` once the server has received and processed `SynchronizeComplete` | [Timing considerations](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/timing-considerations.html) |
| The server's awareness of client-side completion lags by roughly half an RTT (tens–hundreds of ms) | Don't assume the server "knows" a client synchronized/loaded the instant that client's local callback fires | [Timing considerations](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/timing-considerations.html) |
| Additive load order: server loads the scene and spawns its in-scene `NetworkObjects` first, *then* sends `Load` to clients; each client sends `LoadComplete` independently; server broadcasts `LoadEventCompleted` only after every client has reported in | The server's own scene content exists before any client is told the load even started | [Timing considerations](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/timing-considerations.html) |
| In-scene placed `NetworkObjects` run `Awake` then `Start` during Unity's own scene load; NGO spawns them (and fires `OnNetworkSpawn`) only after scene loading finishes | Don't rely on network state (ownership, `NetworkVariable` values) inside `Awake`/`Start` of an in-scene placed object — it isn't spawned yet | [Timing considerations](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/timing-considerations.html), [In-scene placed NetworkObjects](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/inscene-placed-networkobjects.html) |
| `LoadSceneMode.Single` scene switch: objects with `DestroyWithScene == false` are migrated into `DontDestroyOnLoad` temporarily, then moved into the new active scene once it loads | These objects survive a full scene switch without being destroyed or re-spawned | [Timing considerations](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/timing-considerations.html) |
| Unload order: server despawns objects in that scene locally before sending `Unload`; clients can receive despawn messages before the `Unload` event itself | A client may already show zero `NetworkObjects` in a scene before it's told the scene is unloading | [Timing considerations](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/timing-considerations.html) |
| At RTT ≥ ~500 ms, a `NetworkBehaviour` that fires a client→server message immediately on `LoadComplete` can hit latency-related ordering issues | Test high-latency scene-load paths with simulated network conditions, not just LAN | [Timing considerations](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/timing-considerations.html) |

**Critical caveat**: never use `UnityEngine.SceneManagement.SceneManager.sceneLoaded` to detect "the scene is ready" in networked code — it fires before NGO has spawned the scene's `NetworkObjects`, so code driven off it commonly hits null/not-yet-spawned `NetworkObject`/`NetworkBehaviour` references. Use `NetworkSceneManager`'s own events (`OnLoadComplete`, `OnSynchronizeComplete`, etc.) instead.

## In-scene placed NetworkObjects

| Fact | What it decides | Source |
|---|---|---|
| Initialization order differs by origin: dynamically-spawned prefab → `Awake` → `OnNetworkSpawn` → `Start`; in-scene placed object → `Awake` → `Start` → `OnNetworkSpawn` | A shared `NetworkBehaviour` used both ways can't assume `OnNetworkSpawn` has already run by the time `Start` executes | [In-scene placed NetworkObjects](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/inscene-placed-networkobjects.html) |
| In-scene objects are identified by `GlobalObjectIdHash` + originating scene (not by `NetworkPrefab` registration) | They don't need to be registered in the `NetworkManager`'s prefab list; NGO registers them internally when scene management is enabled | [In-scene placed NetworkObjects](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/inscene-placed-networkobjects.html) |
| Auto-spawn / auto-despawn tied to scene lifecycle | They spawn automatically when their scene loads during an active session, and despawn automatically when their scene unloads — no manual `Spawn()` call needed for the normal case | [In-scene placed NetworkObjects](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/inscene-placed-networkobjects.html) |
| `NetworkObject.Despawn()` default destroys the instance; `NetworkObject.Despawn(false)` despawns without destroying | Use `Despawn(false)` for an in-scene object you intend to keep around and later respawn (e.g. a resettable pickup) | [In-scene placed NetworkObjects](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/inscene-placed-networkobjects.html) |
| `NetworkObject.Spawn(destroyWithScene)` re-spawns a previously despawned-without-destroy instance | The mechanism for "reset and reuse" patterns on in-scene objects | [In-scene placed NetworkObjects](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/inscene-placed-networkobjects.html) |
| Migrating an already-spawned in-scene object into a different scene causes "soft synchronization errors" for late-joining clients | Don't reparent/move in-scene placed objects across scenes at runtime after they've spawned; treat them as scene-bound | [In-scene placed NetworkObjects](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/inscene-placed-networkobjects.html) |
| "Auto object parent sync" is toggleable; scale is always treated as local-space relative for pre-parented in-scene objects | Affects how parent/child transform sync behaves specifically for objects that were already parented in the Editor scene | [In-scene placed NetworkObjects](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/inscene-placed-networkobjects.html) |
| Not recommended for objects that get frequently destroyed, migrated between scenes during full scene switches, or repeatedly re-parented | Use dynamically-spawned prefabs instead for anything with that lifecycle | [In-scene placed NetworkObjects](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/inscene-placed-networkobjects.html) |

### Custom scene management (scene management disabled)

| Fact | What it decides | Source |
|---|---|---|
| Disabling "Enable Scene Management" forces all loads/unloads through raw `UnityEngine.SceneManagement.SceneManager` | Nothing about scene events, in-scene object sync, or auto-migration is handled by NGO anymore — it's entirely the developer's responsibility | [Custom scene management](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/custom-management.html) |
| On connect, a client deletes any in-scene placed `NetworkObjects` already present in scenes it has currently loaded | Prevents duplicate/unsynchronized in-scene objects, but means the developer must re-provide that content deliberately | [Custom scene management](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/custom-management.html) |
| Scenes loaded after the client already connected do **not** get their in-scene `NetworkObjects` auto-synced | Recommended workaround: dynamically spawn network prefab instances instead of relying on in-scene placement, once past initial client sync | [Custom scene management](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/custom-management.html) |
| Edits to in-scene placed Network Prefabs are not automatically synchronized to clients | Override `NetworkBehaviour.OnSynchronize` to manually serialize whatever property updates need to reach clients | [Custom scene management](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/custom-management.html) |
| Developer must drive their own sync via `NetworkManager.OnClientConnectedCallback`, custom `INetworkSerializable` messages/RPCs, both `LoadSceneMode.Additive` and `.Single` as needed | This is the full scope of what integrated management otherwise gives you for free | [Custom scene management](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/basics/scenemanagement/custom-management.html) |

## Session management and reconnection

| Fact | What it decides | Source |
|---|---|---|
| `NetworkManager`'s `clientId` is not a stable player identity — it's assigned on connect and freed on disconnect; a later, unrelated player can be assigned the same value | Never key persistent player data (inventory, progress, reconnect state) by `clientId` alone | [Session management](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/advanced-topics/session-management.html) |
| Recommended persistent identity: an account/login system, or a client-generated `System.Guid.NewGuid()` stored in `PlayerPrefs` and sent to the server on connect | Gives the server a stable key to reassign session data to the correct returning player | [Session management](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/advanced-topics/session-management.html) |
| Two data-preservation patterns: (1) store character state (position, health, etc.) keyed by the persistent player id; (2) maintain a dictionary mapping persistent id → owned `NetworkObjectId`(s) | Determines what a reconnect needs to restore — recreate/reassign the player's state object(s), or re-establish ownership over already-existing ones | [Session management](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/advanced-topics/session-management.html) |
| Session data must be kept up to date and stored host-side while the player is disconnected | The host, not any client, is the source of truth for what gets restored | [Session management](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/advanced-topics/session-management.html) |
| No built-in expiry — NGO does not purge stale disconnected-player data itself | If you want session data to expire, you implement your own timeout/purge logic on top | [Session management](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/advanced-topics/session-management.html) |
| Reconnect trigger: `NetworkManager.OnClientDisconnectCallback` (or a custom event), and check `NetworkManager.ShutdownInProgress` before attempting to reconnect | Prevents starting a reconnect attempt while a shutdown from the previous connection is still unwinding | [Reconnecting mid-game](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/advanced-topics/reconnecting-mid-game.html) |
| Must explicitly guard against auto-reconnecting after: an intentional quit, a normal server shutdown, a client kick, or a connection-approval denial | Without these guards, a reconnect loop can keep firing after conditions where reconnecting is never appropriate | [Reconnecting mid-game](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/advanced-topics/reconnecting-mid-game.html) |
| If the client's current active scene name matches the server's active scene name at sync time, NGO does **not** single-load that scene — it treats it as already present and only additively loads the server's remaining scenes | Any additive scenes the client already had loaded before disconnecting are not cleared, and can end up duplicated | [Reconnecting mid-game](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/advanced-topics/reconnecting-mid-game.html) |
| `NetworkSceneManager.VerifySceneBeforeLoading` doubles as a duplicate-load guard on reconnect | Same delegate used for scene validation (see basics table above) can reject a redundant scene load during reconnection | [Reconnecting mid-game](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/advanced-topics/reconnecting-mid-game.html) |
| Boss Room sample implements reconnection as a state machine with a `ReconnectCoroutine` that retries sequentially until success, a max-attempts limit, or user cancellation | Reference pattern for structuring retry/backoff logic instead of a single blind reconnect attempt | [Reconnecting mid-game](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/advanced-topics/reconnecting-mid-game.html) |

**Critical caveat**: a reconnecting client that still has its previous session's additive scenes loaded, and whose current scene name happens to match the server's active scene, will silently accumulate duplicate additive scene instances — because NGO skips the single-mode reload for a "matching" active scene. Explicitly unload the client's additive scenes on disconnect (or reconnect) rather than assuming synchronization will reconcile scene state for you.

### Mitigating duplicate additive scenes on reconnect

None of these is automatic — pick one deliberately rather than assuming default sync behavior handles it:

| Mitigation | Trade-off | Source |
|---|---|---|
| Load a different scene in single mode on disconnect | Guarantees the client's active scene no longer matches the server's, forcing a clean single-load on reconnect; requires a dedicated "disconnected" scene | [Reconnecting mid-game](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/advanced-topics/reconnecting-mid-game.html) |
| Unload additive scenes on disconnect | Removes the stale content immediately, before any reconnect attempt begins | [Reconnecting mid-game](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/advanced-topics/reconnecting-mid-game.html) |
| Unload additive scenes on reconnect, before rejoining | Defers cleanup until a reconnect is actually attempted, avoiding wasted work if the player never reconnects | [Reconnecting mid-game](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/advanced-topics/reconnecting-mid-game.html) |
| Use `VerifySceneBeforeLoading` to reject the redundant load | Simplest to wire up, but does **not** by itself handle scenes the server unloaded while the client was away — combine with one of the above for full coverage | [Reconnecting mid-game](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.13/manual/advanced-topics/reconnecting-mid-game.html) |

The session-management manual pages are relatively thin — they describe the pattern conceptually (persistent id, host-side data, reassignment on reconnect) without prescribing a concrete `SessionConfig`-style API; treat the two data-preservation patterns above as the extent of what's documented, not an exhaustive API surface.
