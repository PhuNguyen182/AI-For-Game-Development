## Ignore surface

The `Regenerated by` column is what makes each entry safe to discard: an entry
Unity or a toolchain rebuilds costs time to lose, never content.

| Entry | Reason to ignore | Regenerated by | Source |
|---|---|---|---|
| `Library/` | Unity's own instruction: "Exclude the `Library` folder from version control, because it's unique to your computer and is a working directory for your project" | Unity — "You can delete the `Library` folder … Unity regenerates the folder the next time you open the project" | [Default project directories](https://docs.unity3d.com/Manual/default-directories.html) |
| `Temp/` | Unity's own instruction: "Exclude this folder from version control" | Unity — "a folder for temporary data, which gets cleared every time you close Unity" | [Default project directories](https://docs.unity3d.com/Manual/default-directories.html) |
| `UserSettings/` | Unity's own instruction: "Exclude from version control to avoid overwriting your teammates' personal Unity preferences" | Unity, per user, on first use | [Default project directories](https://docs.unity3d.com/Manual/default-directories.html) |
| `Logs/` | Per-machine Editor log output; nothing here is project state, and it churns every session | Unity, on every Editor run | [Default project directories](https://docs.unity3d.com/Manual/default-directories.html) |
| `Obj/`, `obj/` | Intermediate compiler output for the generated C# projects; a build artifact by definition | The C# toolchain, on every compile | synthesized |
| `Build/`, `Builds/`, `[Bb]uild[s]?/` | Player output — large, binary, and reproducible from the tracked sources; the bracketed form catches the casing variants at once so no local convention slips through | The build pipeline | synthesized |
| `*.csproj`, `*.sln` | Generated per machine from the assembly definitions and package set; committing them means a merge conflict on every package change and a solution that references paths another machine does not have | Unity, whenever assemblies or packages change | synthesized |
| `*.userprefs` | Per-developer IDE state (open documents, breakpoints) that carries no project meaning | The IDE | synthesized |
| `.vs/`, `.idea/` | Per-developer IDE caches and indexes, large and constantly rewritten | Visual Studio / JetBrains Rider | synthesized |
| `*.apk`, `*.aab` | Android build artifacts — large binaries reproducible from source, and the exact class of file that quietly bloats history permanently | The build pipeline | synthesized |
| `*.unitypackage` | An export of assets already tracked in `Assets/`, so committing one stores the same content twice | Manual export | synthesized |
| Crash-report folders (`sysinfo.txt`, `crashlytics-build.properties`, `*/Crashes/`) | Per-machine diagnostic dumps written after a fault; never project state, and they can contain machine and path details worth not publishing | Unity / the crash handler, on a fault | synthesized |

**Critical caveat**: `.gitignore` only governs files git is not *already*
tracking. An entry added after something was committed has no effect until the
path is removed from the index. Adding `Library/` to `.gitignore` on a
repository that already tracks it changes nothing visible, so the churn appears
to be the ignore rule failing rather than a stale index entry.

## Track surface

| Entry | Reason to track | Source |
|---|---|---|
| `Assets/` | The project's content and code, including every `.meta` — the GUID identity that references resolve through, per [meta-files-and-guids.md](meta-files-and-guids.md) | [Default project directories](https://docs.unity3d.com/Manual/default-directories.html) |
| `ProjectSettings/` | Project-wide configuration — physics, quality tiers, player settings, layers, input — that must be byte-identical across machines, or the same code behaves differently per clone. Distinct from `UserSettings/`, which is the per-developer folder Unity says to exclude | [Default project directories](https://docs.unity3d.com/Manual/default-directories.html) |
| `Packages/manifest.json` | The project manifest the Package Manager "reads so that it can compute a list of which packages to retrieve and load" — the declared dependency set | [Project manifest file](https://docs.unity3d.com/Manual/upm-manifestPrj.html) |
| `Packages/packages-lock.json` | The resolved dependency graph, which is what makes resolution deterministic rather than "whatever resolved today"; Unity recommends putting lock files under source control | [Lock files](https://docs.unity3d.com/Manual/upm-conflicts-auto.html) |
| `.gitattributes` | Carries the LFS filters and the merge-driver selections; an untracked one means every clone silently loses both | [Git Large File Storage](https://git-lfs.com) |

## Single-decision conflict files

Both files below hold one project-wide choice. Git will happily produce a
three-way text merge of either, and the result is a value that no machine ever
had — which is worse than a conflict, because it looks resolved.

| File | Content | Why a text merge is invalid | Resolution | Source |
|---|---|---|---|---|
| `ProjectSettings/ProjectVersion.txt` | The Editor version the project was last opened with, as `m_EditorVersion` and `m_EditorVersionWithRevision` | The two lines are one fact stated twice; a merge can pair a version string with the other side's revision hash, naming an Editor build that does not exist | Decide which Editor version the team is on and take that side whole; the Editor rewrites the file on next open anyway, so the commit only records the decision | synthesized |
| `Packages/packages-lock.json` | The full resolved dependency graph with a hash per package | Unity's own rule: "Don't manually modify the lock file: the Package Manager creates and maintains the lock file, so it overwrites any changes you make to the file." A merged graph is a resolution the resolver never produced, and the per-package hashes will not match what a merged version claims | Take one side whole, then let the Package Manager regenerate it by opening the project — or delete it and let resolution rebuild it from `manifest.json` | [Lock files](https://docs.unity3d.com/Manual/upm-conflicts-auto.html) |

| Related fact | Bearing on the decision | Source |
|---|---|---|
| `enableLockFile` in the project manifest | Locking can be turned off; a project with it disabled has no lock file to conflict over, at the cost of non-deterministic indirect-dependency resolution | [Project manifest file](https://docs.unity3d.com/Manual/upm-manifestPrj.html) |
| `resolutionStrategy` and `pinnedPackages` in the project manifest | Recurring lock-file churn is often a resolution-strategy question rather than a merge problem — pinning removes the churn at its source | [Project manifest file](https://docs.unity3d.com/Manual/upm-manifestPrj.html) |
| A recurring `ProjectVersion.txt` conflict | Two people are on different Editor versions; the conflict is the symptom, and the fix is agreeing a version, not a better merge | synthesized |

**Critical caveat**: `ProjectVersion.txt` conflicts are not cosmetic. Whichever
version wins, opening the project in a *newer* Editor triggers an irreversible
project upgrade — asset reimports and setting migrations that the older Editor
cannot read back. Deciding this file is a team decision, not a merge cleanup.

## Git LFS attributes

LFS "replaces large files such as audio samples, videos, datasets, and graphics
with text pointers inside Git, while storing the file contents on a remote
server."

```gitattributes
*.png  filter=lfs diff=lfs merge=lfs -text
*.psd  filter=lfs diff=lfs merge=lfs -text
*.tga  filter=lfs diff=lfs merge=lfs -text
*.exr  filter=lfs diff=lfs merge=lfs -text
*.fbx  filter=lfs diff=lfs merge=lfs -text
*.wav  filter=lfs diff=lfs merge=lfs -text
*.mp3  filter=lfs diff=lfs merge=lfs -text
*.ogg  filter=lfs diff=lfs merge=lfs -text
*.mp4  filter=lfs diff=lfs merge=lfs -text
```

| Token | Meaning | Source |
|---|---|---|
| `filter=lfs` | Selects the clean/smudge filter pair named `lfs` that `git lfs install` registers — this is what actually substitutes pointer for content | [git-lfs-install](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-install.adoc) |
| `diff=lfs`, `merge=lfs` | Routes diff and merge through LFS rather than letting git attempt either on the pointer text | [gitattributes](https://git-scm.com/docs/gitattributes) |
| `-text` | Unsets text processing, so no end-of-line conversion is ever applied to a binary — git's own binary macro is `[attr]binary -diff -merge -text` | [gitattributes](https://git-scm.com/docs/gitattributes#_end_of_line_conversion) |
| `git lfs track "*.psd"` | Writes such a line for you rather than editing the file by hand | [Git Large File Storage](https://git-lfs.com) |
| `git add .gitattributes` | Required — the page states users "must ensure `.gitattributes` is tracked"; an untracked one means no clone applies these filters | [Git Large File Storage](https://git-lfs.com) |
| `*.meta` must **not** be listed | A `.meta` is small text holding the GUID identity; routing it through LFS makes the identity of every asset depend on the LFS remote | synthesized |

**Critical caveat**: adding a pattern to `.gitattributes` converts nothing
already committed. History keeps the full binaries, and only newly staged files
go through the filter. Converting existing history requires `git lfs migrate`,
which rewrites commits — a history rewrite that belongs to `git-recovery` and
`git-safety-anchor`, not to an attribute edit.

## The pointer-file symptom

| Observation | What it means | Source |
|---|---|---|
| A texture or model is a small text file (roughly 130 bytes) instead of megabytes | It is the pointer, not the object — LFS "replaces large files … with text pointers inside Git" | [Git Large File Storage](https://git-lfs.com) |
| Its first line is `version https://git-lfs.github.com/spec/v1`, followed by `oid sha256:<hash>` and `size <bytes>` | This is the canonical pointer format; the `size` line states what the real file should be | [git-lfs-fsck](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-fsck.adoc) |
| `git status` reports the tree clean | The pointer *is* the committed content as far as git is concerned, so there is nothing for git to report — this is the failure mode that reaches a build unnoticed | synthesized |
| Unity shows the asset as corrupt, or imports it as a broken placeholder | The importer received text where it expected binary; the asset's `.meta` and GUID are intact, so this is not a reference break | synthesized |
| `git lfs install` was never run before the clone | Without the smudge filter configured, the checkout writes pointers; the docs note this "requires a manual `git lfs pull` every time a new commit is checked out on your repository" | [git-lfs-install](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-install.adoc) |
| The whole working tree holds pointers | The clone predates `git lfs install`, or `GIT_LFS_SKIP_SMUDGE` was set; run `git lfs install` then `git lfs pull` rather than re-cloning | [git-lfs-install](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-install.adoc) |

## LFS command surface

| Command | What it does | Use when | Source |
|---|---|---|---|
| `git lfs install` | Sets up the clean and smudge filters named `lfs` in the global git config and installs a pre-push hook that runs `git-lfs-pre-push`. Run once per user account | Before the first clone of an LFS repository on a machine | [git-lfs-install](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-install.adoc) |
| `git lfs env` | Prints the resolved LFS environment and configuration | Confirming the filters are actually configured, before blaming the remote | [git-lfs-env](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-env.adoc) |
| `git lfs ls-files` | Lists LFS files in the tree at a given ref, with a marker per entry: `*` "indicates a full object", `-` "indicates an LFS pointer" | The single fastest check for whether the tree holds content or pointers — every `-` is an unusable asset | [git-lfs-ls-files](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-ls-files.adoc) |
| `git lfs fsck` | "Checks all Git LFS files in the current HEAD for consistency", moving corrupted files to `.git/lfs/bad`. `--objects` verifies each object's hash and on-disk presence; `--pointers` verifies canonical pointer format; `-d`/`--dry-run` checks without moving anything | Before declaring a checkout complete, and whenever an asset is suspected corrupt rather than merely absent | [git-lfs-fsck](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-fsck.adoc) |
| `git lfs pull` | Downloads missing LFS content from the remote and writes it into the working copy | The tree holds pointers and the objects are not in the local store | [git-lfs-pull](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-pull.adoc) |
| `git lfs checkout` | "Update working copy with file content if available" — scans the current ref and writes real content wherever a file is missing or holds pointer content with the same SHA. Explicitly "does not download any content" | The objects are already in the local store but the working tree still shows pointers | [git-lfs-checkout](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-checkout.adoc) |
| `git lfs fetch` | Downloads objects into the local store without touching the working copy | Pre-warming the store; pair it with `git lfs checkout` to materialise | [git-lfs-checkout](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs-checkout.adoc) |

**Critical caveat**: `git lfs pull` and `git lfs checkout` are not
interchangeable. `checkout` cannot fix a missing object because it downloads
nothing, and running it against an empty local store reports success while
leaving every pointer in place — the exact shape of a verification that
verified nothing. Confirm with `git lfs ls-files` that no `-` marker remains.

Every check on this page is a repository-level check, and none of it proves the
Editor can import what was restored — that confirmation is still owed
separately, and a working-tree rewrite to obtain it must happen with the Editor
closed.
