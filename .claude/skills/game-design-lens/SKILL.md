# Game design lens

- **Not for:** how shipped games solved it (`design-precedent-sweep`), priority (`product-quality-bar`), revenue (`monetization-modeling`).
- **Sources:** the GDD at `CLAUDE.md` → GDD path, playtest evidence, the reference games in `CLAUDE.md`, the data pack.

## Steps
1. **State the intended feeling first:** one sentence on what the player should feel and when; no such statement in the GDD → that is finding F1.
2. **Trace the loop:** action → feedback → reward → next decision; name where it breaks or where a step gives the player no decision.
3. **Read progression:** what grows, how fast, and where it stalls; a wall needs a reason the player can understand.
4. **Read difficulty:** a level or wave funnel when the pack has one, otherwise the GDD's stated curve as `[assumption: ...]`.
5. **Read FTUE:** time to first meaningful decision, what is taught by play and what by text.
6. **Read session shape:** session length against `CLAUDE.md` audience and input; where a player can stop feeling done.
7. **Separate rules, data and presentation:** say which layer a recommendation changes, so its build cost is visible.
8. **Say what a playtest settles:** each claim about feel names the playtest question that tests it.

## Never
- **Mechanic for its own sake:** recommending a mechanic with no stated feeling or loop effect.
- **Genre copying:** "competitors have it" alone is no reason; state what it does for this loop.
- **Designing for the metric:** a change that lifts a number by hurting the stated feeling is a conflict, shown as one.

## Example
- **"Add an energy system to slow players":** challenged — stated the feeling it breaks, asked what problem pacing solves, and listed alternatives for `researcher` to find precedents on.
